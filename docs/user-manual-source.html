SmartCodeGenerator

User Manual

A command-line assistant that turns plain-English descriptions and existing data into working .NET projects.

1. About this manual

SmartCodeGenerator is an interactive command-line tool. You type instructions in ordinary English — create employee class, build app: a library that lends books to members — and it creates or edits real .NET code on disk.

This manual covers the tool as an end user meets it: how to start it, what each command does, and how to drive the two flows that do the most work — generating a whole application, and editing the classes of a project. Chapter 19 is a complete command reference you can skim.

2. Getting started

Starting the tool

Ask it for its version with CodeGenerator --version, or for the command overview with CodeGenerator --help (-h and /? also work), without entering the prompt at all.

Run the executable with no arguments and it prints three lines — the first naming the version you are running — and the prompt:

CodeGenerator >>

Type help for an overview of what the tool can do, and exit to leave. Press TAB at the prompt for command suggestions.

Stopping something, and long output

Ctrl-C asks rather than kills. The first press cancels what is running and lets any file being written finish, so you are never left with a half-created project; the tool says so and returns you to the prompt. Some work cannot be interrupted once started — a compile already running, for instance — so a second Ctrl-C quits outright.

Any command still running after a moment says so, with the seconds counted, so a pause never looks like a hang:

CodeGenerator >> create class Customer
Working | 2s

It appears only once a command has taken longer than a moment, so the many that return at once show nothing extra, and it leaves the time it took in the transcript when it finishes. The same indicator covers the longer jobs that always had one — discovering a domain, compiling a generated app. Output longer than the window — help all, or a large candidate model — stops a page at a time; press Enter for more or q to stop. Both are skipped when output is redirected, so scripts and saved transcripts are unaffected.

Colour, and turning it off

Output is colour-coded, in four colours and no more:

ColourWhat it meansExamples
GreenSomething was produced.A class written, a validator generated, a validation rule registered, an application generated.
YellowSomething you can fix. Nothing failed.No project selected; a class that does not exist; a command the tool does not recognize; a missing Wikipedia store.
RedSomething failed.A generated application that will not compile; an unexpected error.
GreySecondary detail you are not required to read.Paths and labels beside the thing they describe.

A command you mistype is yellow rather than red on purpose: nothing has gone wrong with the tool, you have simply typed something it does not know.

Colour is switched off automatically when you redirect output to a file or another program, so a saved transcript is ordinary text. To turn it off at a real console as well, set the NO_COLOR environment variable to anything at all — the convention is that its mere presence is the instruction, so even NO_COLOR=0 means no colour. Conversely, set FORCE_COLOR to keep colour even when output is redirected, for a program that captures the output and colours it itself.

If you see no colour

Run status. The Colour line says whether colour is on and, if it is, how it is being sent:

What it saysWhat it means
on (ANSI escape sequences)The usual case on a modern terminal. If text is still not coloured, the terminal itself is discarding it — check its colour scheme, and whether Windows high-contrast mode is on.
on (Windows console attributes)An older console that cannot handle escape sequences. Colour is being set the legacy way.
off (NO_COLOR is set to '…')Something set that variable — possibly your PowerShell profile. Remove-Item Env:NO_COLOR clears it for the session.
off (output is redirected…)The output is going to a file or another program. Set FORCE_COLOR if that program renders colour.

One check settles whether the tool is at fault: Write-Host "test" -ForegroundColor Red at a PowerShell prompt. If that is not red either, no program can colour text in that terminal and the cause is the terminal or its settings.

A quiet start is a healthy one. The tool reports its own state only when something is wrong with it — a missing Wikipedia store, nothing updating it, an AI model it was told to load and could not. So if all you see is those three lines, everything it depends on is in order. Type status at any time for the full picture. Earlier versions printed that picture at every launch, which meant the warnings in it were easy to skim past.

Where your work is saved

Everything the tool creates goes under a single folder called the workspace root. It is chosen like this, in order:

  1. the PROJECTPATH environment variable, if it is set;
  2. otherwise the current directory — and if you launched from a build-output folder such as bin\Debug\..., the tool climbs out of it so generated code does not end up buried there.

Check yours before you generate anything. On Windows, echo %PROJECTPATH% tells you where your projects will appear. Setting it once saves confusion later, because the tool reports the full path of everything it writes and that path will not be your current directory if the variable is set.

Running a single command without the prompt

Pass a command as an argument and the tool runs just that command and exits, through exactly the same pipeline as the interactive prompt:

CodeGenerator "create console project EmployeeManagement"

Scripting the tool

You can pipe a sequence of commands into the tool. When input is piped, it never prompts — every question that would normally be asked is skipped, so a script always produces the same result. Anything you would have answered interactively must instead be typed on the command line (see chapter 7):

build app: a shop that sells books company "Codis Ltd" theme dark
approve console
exit

3. Core ideas

Projects

A project is an ordinary .NET project on disk, inside your workspace root. One project is current at a time, and class commands act on it. Use list projects, use project <name> and current project to move around.

Two ways to create code

FlowUse it whenChapter
build appYou want a whole working application — model classes, data access, validation and a front end — from a description or a data file.4–8
Project and class commandsYou want to build up or edit a project piece by piece: classes, properties, methods, interfaces, validation rules.9–11

The .codegen folder

The tool keeps small files of remembered state beside your work, including the customization answers it offers back to you next time (.codegen/app-profile.json, chapter 7). They are safe to delete; you will simply be asked again.

4. Building an application: the workflow page

The build app command is the centre of the tool. It works out a candidate set of classes, shows them to you, and only writes code once you approve.

It opens in your browser. The console prints an address, says that Ctrl-C cancels, and waits; everything from there to the finished application happens on that page. Nothing is sent anywhere — the page is served by the tool itself, on this machine, and closes when the command ends.

Starting it

CommandEffect
build appOpens the page on the description, with nothing filled in.
build app: <description>Skips the description — you have already answered it — and opens on the application type.

No browser? Set CG_NO_WEB=1 and the command asks its questions in the console instead, as it did before. A run whose input is piped or redirected from a file also stays in the console, so existing scripts keep working exactly as they did.

The stages

The page draws the whole build as ten connected stages, so you can see where you are and what is still to come. The stage being answered is open beneath the diagram; the others are named and greyed until they are reached.

  1. Describe — what you are building, in plain English: a library that lends books to members. Leave it blank if you are pointing at a data file instead.
  2. Application Type — which kind of application; see chapter 8.
  3. Data — a file to read, or discovery from the web. Naming a file makes it the source of truth for the model (chapter 5), and the page says what that file holds — orders.csv: orders — 240 rows, 12 columns — before you commit to it.
  4. Look — branding, theme, layout and the optional layers, all behind one checkbox and all optional (chapter 7).
  5. Discover — the classes are worked out, from your description or from your file.
  6. Review classes — the model, on screen, where you change what the classes are called and what is in them before anything is written (chapter 6, and Changing the model on the page below).
  7. Output — what will be written: how those classes connect, drawn; which of them get a screen of their own; and what will be generated, with the single command line that would do the same run again. The last look before anything is written.
  8. Entry Template — how a business-shell entry form arranges its fields. Always on the diagram, but it only asks when the target is WPF and the layout is business; otherwise it says the choice does not apply. Grouped is the default.
  9. Generate — the project is written and compiled, with its build log on screen as it happens (see Knowing it is still working below).
  10. Run — the finished application is started, so you see it working rather than being told that it compiled. It runs as a separate process and keeps running after the page closes. A class library, or a project that did not build, says so here instead: there is nothing to start. While it is running the page offers to stop it, with the process id beside the offer — worth doing before building that project again, because a running application holds its own output folder open.

Getting around

There are no Back and Next buttons. The boxes are how you move:

BoxWhat it means
Green, tickedAnswered. It shows the answer it holds — Console, orders.csv, 12 classes — and clicking it goes back to change that answer.
Blue, openThe one you are answering. It carries both moves: the step forward — Continue →, or the name of the step where it has one, as Generate does — and a quiet ← back to the stage before it.
Dashed outlineWhere that step leads. Clicking it does the same thing as the button in the open box, so you can move by clicking either.
GreyNot reached yet, or nothing in it to go to: it says what it will ask, and cannot be clicked. Generate and Run stay like this until the project has actually been written — Write it is what enables them.
RedSomething went wrong there — a file that would not read. Click it to try again.

The step forward is greyed out until the answer is usable, so a colour that is not a colour stops you there rather than three screens later. Writing the application is deliberately not something a click on a box can do: the Generate box only opens through the button in the review box, and only after Write it has run does the Run box become something you can move to. Going back keeps what the open box had already answered, and costs nothing except where it must: changing the description or the data source throws away the model that was discovered from the old one, because it was worked out from something you have since changed, and that stage runs again. Changing the application type or anything under Look costs nothing at all, because neither is read until the project is written.

You need not reach for the mouse. The panel that opens takes the keyboard, and Enter takes the step the open box is offering. It only ever takes an ordinary step: Generate and Run are actions rather than movement, so they stay deliberate clicks, and Enter in the description is a new line, as it is anywhere else.

Cancel ends the whole run, and asks before it does once there is an answer to lose — it counts the classes it would discard, and says plainly when the project has already been written, because cancelling does not delete that. On a first page with nothing answered yet it simply cancels.

How the page ends

Done on the last box ends the run. The page replaces the diagram and the panel with what the console is about to print — where the project was written, the next steps, and the command that would do the same run again — and tells you the tab can be closed. Your prompt comes back at the same moment.

The page then goes quiet, and that is expected rather than a fault: it is served by the tool itself, so it has nowhere to be served from once the run is over. Nothing is lost by leaving the tab open, and nothing is lost by closing it. If the connection goes at any other time — the tool stopped, or the command was interrupted — a bar along the bottom says so.

The browser tab says which stage you are on — 3 of 10 · Data — so two tabs on one workflow are told apart at a glance.

Picking up an unfinished build

The workflow lives in the browser, and a browser tab is easy to close by accident. What that used to cost was everything the build was holding — and the part worth minding was never the discovery, which can be run again in a minute, but the edits: eight classes renamed, the invented fields deleted, three suggestions promoted, two classes moved across the master/transaction split. None of that has a command-line form, so the same run as a command line could never bring it back.

It is now saved as you work, after every answer and every edit, and the next build app in that workspace offers it:

An unfinished build is waiting in this workspace:
  "a shop"  -  WPF  -  8 classes reviewed
  left off at Review, 20 minutes ago

  [r]esume   start [f]resh   [d]iscard

Enter starts fresh, and deletes nothing — the build you left is still there to be offered next time. Only discard removes it. A workspace keeps one unfinished build, so the fresh run is not saved as you go — the console says so. Starting fresh is the default deliberately: resuming a build you had forgotten about could have you generate an application from a stale model, or from a colleague's abandoned session.

Your data is not saved — only where it came from

The snapshot holds your answers and your model. It does not hold the rows that were read, so it stays a few kilobytes whether the source had ninety rows or twenty-five thousand, and none of your data is copied into .codegen. Resuming re-reads the source instead.

That has two consequences worth knowing. A file that has moved since cannot be re-read, so the build resumes on the Data stage with the old path named, rather than failing. And a SQL Server connection string is never saved at all — so a resumed database build names the database and asks for the connection again.

A build that finishes, or that you cancel, clears its snapshot. One you abandon by closing the tab keeps it, which is the whole point. Piped runs neither write a snapshot nor read one, so a script stays deterministic.

Changing the model on the page

The Review classes stage draws one card per class, and everything on a card can be corrected in place. Nothing is written until you leave the stage, so this is the cheap moment to fix a name that discovery got nearly right. Each card carries a coloured tag for the kind of thing the class is — Item, Party, Transaction, Document, Place, Device — which is what decides whether it may hold a link to another class.

The relationship diagram and the screen each class will get are on the Output stage next door, along with what will be generated. They were on this page once, under a full screen of cards; a confirmation you reach by scrolling past the thing being confirmed is not a confirmation.

To do thisDo this on the card
Rename a classType over its name in the card's heading.
Delete a classremove, beside the name.
Rename a propertyType over it in the property's own row.
Change a property's typeThe drop-down beside it — string, int, decimal, bool or DateTime.
Delete a propertyThe × at the end of its row.
Add a propertyThe row under the last one: a name, a type, then add field.
Add a classadd class, under the cards.

Changing a type is the one worth knowing about. The type of every property is a guess made from its name, and the guess is sometimes wrong in a way that only shows up once the application is running — Servings reads as text and means a number. This is the last screen before the class is written, so it is the last cheap place to say so.

An edit the tool cannot make is refused with the reason on screen, and the box goes back to what the model actually holds — so what a card shows is always what will be generated. A property may not be called Id, which is generated for you; nor share its class's name, which C# does not allow; nor take a name another property on that class already has. Two properties are also protected from deletion: a class's Name, and whichever property is its last, because a class with neither generates a grid whose only column is a read-only Id and nothing you can type into.

When a step goes wrong

A step that fails turns its box red and says why, and the box stays clickable: go back into it, fix what it was given, and carry on. Nothing about a failure ends the run. A file that is open in another program, a path too long for Windows, a dropped file over the 10 MB limit — each says which of those it was.

Two cases worth knowing by name:

  • No dotnet on PATH. The project is written and simply not compiled; the page says so, and the steps below tell you how to build it yourself. It is not reported as a build that failed, because nothing was built.
  • A file you dropped is too big. Put its path in the Path box instead — the page is served by the tool on your own machine, so a local file never needs copying.

Whatever happens, the console signs off with the command that would do the same run again — description, data source and every option you chose, as one line you can keep or put in a script. The Output stage shows it too, under The same run as a command.

Knowing it is still working

Three of the stages take real time: discovery — asking the local model can take a minute or two, longer still if it has sat idle and has to be reloaded first — writing the project, and compiling it. None of them leaves you looking at a still page.

Each one names what it is doing with the seconds counting up beside it, and ticks itself off when it is done, so the panel reads as a short list of what has happened and what is happening now:

✓ Wrote 96 file(s)
· Compiling it — a first build restores packages and can take a minute — 14 s

While the build runs, the compiler's own output appears line by line underneath, so a build that is going to fail starts telling you before it finishes. A first build restores packages and is the slow one; later builds of the same project are quick.

Discovery

From a description, the tool asks a local model — Ollama, running on your own machine — which classes the domain needs. Answering can take a minute or two, longer the first time in a while if the model has to be loaded first; the page says so while it waits. If no model is configured, or it does not answer, the tool falls back to a local Wikipedia knowledge store instead — reading it, and fetching from Wikipedia the first time it meets a topic, which is its own wait the first time. Either way you are told which one actually produced the classes, on the console and on the review screen: Classes from qwen2.5:3b (Ollama). normally, or, on a fallback, Classes from Wikipedia (fallback). qwen2.5:3b (Ollama) was configured but did not answer. Falling back to Wikipedia. — the reason is always given, never just the fact that it happened. What it settles on goes straight into the review stage, where you can add to it, take from it, and ask about it before anything is written.

To see what it decided, use why there. On its own it groups every decision by outcome — the classes it kept, the ones it suggested and passed over, the ones it rejected — and why <name> shows one name's whole trail: the stage, the reason, and the evidence (chapter 6).

On the Wikipedia path, if no topic is recognized the tool says so and shows only the classes it took from your words. A very short description — two or three words — often finds nothing. Add a few more words about what the system does, or add the classes by hand in the review loop.

Configuring discovery

Which source discovery uses, and how, is read from discovery.json beside the tool's own .exe — the same folder and the same pattern as ai.json (chapter 12). It is optional: a missing or unreadable file is silently treated as the defaults below, so a fresh install works with nothing to configure.

Installing Ollama and pulling the model

Install Ollama from ollama.com — it runs as a background service once installed, with no separate step to start it. Then pull the default model from a console:

ollama pull qwen2.5:3b

To use a different model instead, pull it the same way and set Model in discovery.json to match. Before it commits to Ollama the tool checks, quickly, that the configured model is actually in ollama list — a reachable Ollama with the wrong (or no) model pulled falls back to Wikipedia exactly as an unreachable one does, rather than failing partway through with no classes.

Two passes, and why

A local model on a machine with no usable graphics card generates only a few tokens a second, so discovery genuinely takes minutes. Because of that it is done in two passes by default. The first asks only which classes exist, with a role and a purpose for each and nothing else — a small answer, so it comes back quickly. The second asks what is inside those classes, which is the long part.

The point is what you can see while you wait. Measured on a point-of-sale system:

Complete class list on screenFinished model
Two passes ("Phases": 2, the default)42 seconds229 seconds
One pass ("Phases": 1)158 seconds — only at the end158 seconds

So the split costs about 45% more in total and buys the class list in a quarter of the time. During the second pass the Discover step lists every class it is going to fill in, ticks each one as its properties arrive, and counts them off ("Filling in the properties — 6 of 12"); the classes still to come are listed below with an open circle rather than a tick, because they have not been written yet. On the command line the same progress appears as a count beside the spinner. Set "Phases": 1 if you would rather have the shortest total wait.

When a run is cut short

If a run is stopped before the model has finished — by TimeoutMinutes, by StallSeconds, or by the connection dropping — nothing already produced is thrown away.

With two passes this degrades particularly well, because the pass that decides which classes exist is the short one and almost always finishes: you keep every class, with properties filled in as far as the second pass got, and the review step says so — for example "4 of 12 class(es) have no properties yet — the pass that fills them in did not finish". A class with no properties still gets an identifier, and you can add fields to it in the review step or simply run discovery again.

Pinning to Wikipedia

Set "Source": "Wikipedia" to skip Ollama and always use the local Wikipedia store. This is the option for a run that must be repeatable — a CI job, a demonstration you will run more than once and expect to look the same — since a local model is a sampled source and Wikipedia's lookup, for a topic it has already met, is not.

5. Building from your own data

If you already have the data, it is a better source than any description: the tool reads the real columns and types instead of guessing. There is no model or Wikipedia lookup on this path, so it is fast and works offline.

Naming the source inline

build app: order tracking from csv D:\data\orders.csv
build app from excel D:\data\shop.xlsx
FormatNotes
csvComma-separated text with a header row.
txtDelimited text.
jsonAn array of objects.

sqlA SQL Server database. The location is a connection string, not a path — see Building from a SQL Server database below.

The location is taken as the rest of the line, because Windows paths contain spaces. Anything you want to add after it must be one of the recognized options in chapter 7 — otherwise it becomes part of the path.

Building from a SQL Server database

The location for sql is a connection string rather than a path. Nothing is read when you give it: the tool lists what the database holds and waits.

Northwind on .\SQLEXPRESS

  [x] dbo.Customers        11 cols        91 rows
  [x] dbo.Orders           14 cols       830 rows
  [ ] dbo.Employees        18 cols         9 rows
  [ ] dbo.__EFMigrations    2 cols         1 rows

  2 of 4 tables, every row of each.

The counts are there because every row of every table you tick is read, with no cap on the read — so the number beside each table is what makes ticking it an informed choice rather than a guess. Ticking nothing reads them all, which is also what leaving tables off a scripted line means.

Reading and seeding are not the same limit. Every row is read, and normalization looks at all of them; the rows written into the generated project as starting data are capped per class, and the build says so out loud when it applies — Imported the first 1000 of 25069 rows from dbo.BulkDeals as seed data. A table of forty million rows is therefore a memory problem at the read, not a seeding one.

A row count shown as — means the login could not read it. That needs the VIEW DATABASE STATE permission; the table can still be read without it.

Two things come across that a CSV export would have thrown away. Column types are the database's own, so none of the guessing described above happens on this path at all. Foreign keys become relationships — read from the constraint that enforces them, rather than inferred from a column being called CustomerId.

The generator has five types, so two mappings lose something and say so: a bigint becomes an int, and a uniqueidentifier becomes a string. Composite foreign keys are skipped rather than half-emitted.

For a scripted run, name the tables on the line. Naming none reads all of them:

build app: order tracking from sql "Server=.;Database=Northwind;Trusted_Connection=True" tables Customers,Orders

A password in the connection string is masked wherever the run is echoed back — on the review page, in the console sign-off, and in the replay line — and the connection string is never written to .codegen/. That means the replay line needs the password typing in again before it will run.

Normalization

Real spreadsheets repeat themselves. The tool inspects what you gave it and reports what it found: a repeating group of columns (Item1, Item2, …), a column that depends on only part of the key, a value that should be its own table. Each finding is offered with an explanation, and you choose which to apply. Applying a finding splits the data into properly separated classes; declining keeps your columns exactly as they are.

Every change you accept is remembered, so why in the review loop can explain a class you never named yourself. When input is piped, add normalize to the command line to accept every finding, or leave it off to accept none — that way a script is deterministic.

Your rows come with it

Rows from your file are written into the generated project as starting data, and loaded on first run. If a row cap applied, the tool says so out loud rather than silently dropping data.

6. Reviewing the model before anything is written

Nothing is generated until you approve. The review loop shows the application type and any customization you chose, then waits. When a console is available you pick actions from a list; when input is piped you type them. The classes themselves are not listed — why is what shows them, and what explains how each one got there.

ActionWhat it does
approve (a)Generates the application. See below for the options.
add <name>Adds a class. The name keeps the shape you type, so add cash register becomes one class.

Interactively, approve asks for the type and (where it applies) the storage backend through pickers, with your earlier choice pre-selected so Enter simply confirms it.

An empty model cannot be generated — if discovery found nothing, add at least one class first.

Adding to an app you already made

Run build app again with more in the description, and when the guard notices the project is already there it now says what is different:

D:\SampleProjects\Shop.Wpf already holds a generated project.
It has 8 class(es); this model has 10, of which 2 are new.

  [a]dd the 2 new   [o]verwrite all   [r]ename   [c]ancel   (Enter cancels)

Answering a writes those two classes — the model, its repository and its validator — together with the few files that list the entities, so the new screens appear. Nothing else is written at all. The run tells you how many files it left alone, because that is the half worth checking:

  Written:
    Models\Supplier.cs
    Data\SupplierRepository.cs
    ViewModels\MainViewModel.cs

  41 file(s) untouched.

It knows what is already there by reading the generated code, not by consulting a file it wrote earlier. So it works on applications made by any earlier version of the tool, and it cannot be wrong about what is on disk.

Your .Custom.cs validator rules are never overwritten by an add, and a class that is already there with different fields is named and left alone — adding will not reconcile it and overwriting would, so the choice stays yours. a is offered only when the model really does contain something new: an answer that would do nothing is not put on the menu.

In an application generated before this version, that same rule is what leaves it unable to compile until you change a line in each stub — see Regenerating over an existing project in chapter 8. An add reports it the same way a regenerate does, under Written before the validation pipeline, and kept.

A hand edit inside a generated file that is not .Custom.cs is reverted by an add, just as it is by a regenerate. The list of files written is how you see it happen.

What it cannot recover from the code is your answers: the theme, the layout and the master/transaction split are not in the C#, so they come from the profile in .codegen or from what you chose on this run. And a piped run overwrites in silence exactly as it always has — the question is only asked when there is somebody to answer it.

Relationships between classes

A relationship is not a command you type. It is a shape in the code: the class that owns the relationship carries an int <Target>Id, and beside it a property typed as the target class. Both halves have to be there. With only the identifier, or only the reference, the seeder, the generated validators, the console picker and the master/transaction screen split all see two unrelated classes.

Getting that pair right by hand is fiddly, so the tool does it for you. After any command except creating a class, it reads the classes in the workspace, works out which relationships are missing, and offers to set them. It asks; it never writes without an answer. Creating a class is left alone deliberately, so that entering several in a row is not interrupted.

Three things make the tool believe two classes are related:

  • an int <Target>Id whose target class exists, with no reference beside it — Order.CustomerId where there is a Customer;
  • a property typed as another class with no identifier beside it — an Order holding a Customer Customer and no CustomerId;
  • a class named after another — OrderLine where there is an Order. The longest matching name wins, so SalesOrderLine belongs to SalesOrder rather than to Sales.

Every offer says which two classes and why, in those words, because you are approving a change to your own schema. Say no and that pair is not raised again for the rest of the session; classes you create afterwards are still offered.

14. Signing in to a generated application

Every generated WPF, Windows Forms and web application opens at a login screen. Nothing else in the application is reachable until someone signs in — on the web that includes the home page, and typing a page’s address directly does not get past it.

The first run creates one account, admin, with the password admin. The login screen says so while that password is still in place, and stops saying so once it has been changed. Change it: the account is created for you precisely because an application with no way in is useless, not because the password is a good one.

Passwords are never stored. What is written to the store is a PBKDF2 hash and the random salt it was made with, so reading the data file tells you nothing about anyone’s password.

Roles

An account is either an Admin or a User. The role has exactly two effects:

  • Only an Admin sees the Users screen, where accounts are added, renamed, deactivated and given passwords.
  • Only an Admin can delete a master record.

Both of these are enforced from this version onwards, wherever the delete is asked for — the business shell, all four of the older window layouts, the browser pages and, for the types with no window at all, the repository. Earlier versions showed the rule on some screens and checked it on none, so an application regenerated from an earlier one refuses deletes it used to allow. That is the intended change, not a regression.

Both roles can create, edit and save everything else. A new account is created with no password and cannot sign in until an administrator gives it one — a new account is not a way in until somebody decides it is. Nobody can delete the account they are signed in with, which is also what guarantees an application always keeps at least one administrator.

Turning it off

Add nologin to the build app: line, or answer no to Require a login in the customization step, and the generated application has no login screen, no accounts and no Users screen. Useful for a throwaway prototype; not something to ship.

15. Masters and transactions

A business application has two kinds of screen, and the generator works out which is which from the model it discovered.

A master is reference data — Customer, Product, Supplier, Category. A transaction is a record that refers to reference data and happens at a moment in time — Order, Invoice, Payment. The generator calls something a transaction when it has both a foreign key to another class and either a date of its own or a name it recognises (order, invoice, payment, booking and similar). Both halves are needed: a foreign key alone would make an Address a transaction, and a date alone would make an Employee with a hire date one. Everything else is a master, which is the safe answer — a master screen is the ordinary list this generator has always produced.

A third kind gets no screen at all. A line — OrderLine, InvoiceItem — is a child of a transaction, named after it, and is edited inside its parent rather than on a screen of its own.

What it decided

Every build says so, under the generated project path:

Screens: 2 masters, 1 transaction (Order has 1 line)

Read that line. A class in the wrong group is easy to correct and hard to notice later — and a class listed as a line has no screen, which nothing else in the output would tell you.

You see it when the application actually has those screens — the business shell, or any web application. Under one of the four older window layouts there are no master or transaction screens to have been written, so the build names the layout instead:

Layout: dashboard — no master or transaction screens; the business layout has them.

A type with no window says neither: it has no screens at all.

Correcting it

Name the ones it got wrong. Comma-joined, with no spaces — or in quotes if you prefer them:

build app: a shop that sells books transactions Order,Invoice masters Region

The wizard asks the same two questions, next to the layout question, and remembers your answers in .codegen/app-profile.json. Naming a line entity as a master is how you give it a screen of its own instead of editing it inside its parent. Naming a class both ways is a contradiction, and master wins.

Correcting it in the browser

Typing names is the awkward way round, because both of those questions are asked before discovery has run — you are naming classes you have not seen yet. On the workflow page you do not have to. The Output stage states the screen each class will get, in one table, on card, under its name:

A line is not given the drop-down, because asking for a line to be a transaction is an answer the classifier would drop: it is told which transaction holds it, and offered the one correction that does work.

Only the classes you actually move are recorded. Choosing the screen a class already had leaves nothing behind, which is why the command line at the bottom of the page names the ones you overruled and no others. The consequence is worth knowing: agreeing with the tool does not pin a class, so if you then edit the model such that it classifies differently — taking the date off a transaction, say — it will move. The rail

Down the left is a navigation rail with the same two groups, in the order a rail reads best — Masters, then Transactions — and, for an administrator only, an Admin group holding the Users screen. Line classes are not listed at all: a line is edited inside its parent, which is the whole point of the third kind (chapter 15).

The header names the signed-in user and offers Back and Sign out. Signing out returns to the login screen rather than closing the application, so a second person can sign in at the same machine.

Master screens

A master screen is a read-only list and a dedicated editor. The list finds a record — a search box narrows it across every text column, so you do not have to know which column holds what — and New or Open (or a double-click) opens the editor. Delete acts on the selected row; a master record's delete is available to an administrator only, while a transaction's may also be done by a plain user.

The list cannot be typed into. That is deliberate: an application that edits records two different ways teaches its users that a Customer changes differently from an Order, and this one edits everything one way.

Transaction screens

A transaction screen is the same list with three additions:

  • a date range, labelled with the model's own date — not CreatedOn, which every class carries and nobody chose. A class with no date of its own shows no range rather than filtering on something arbitrary;
  • column totals under the list: every money-shaped column that is neither an Id nor a foreign key gets its own total, over the rows currently shown rather than over the whole store. Several honest totals beat one confidently wrong one;
  • its lines, inside the editor — described below.

The editor

Opening a record replaces the content area. The rail and the header stay where they are, so you always know where you are, and Cancel (or Back) returns to the list. On the web it is an address of its own — /order/7 for a record and /order/new for a new one — which is what makes a record shareable.

The editor works on a copy. Nothing you type reaches the stored record until you press Save, so Cancel genuinely cancels rather than leaving a half-typed record behind. Save runs the same validation rules the rest of the application runs (chapter 10) and says what it refused rather than silently keeping the old value.

Lines

A transaction's editor also holds its lines — the OrderLines of an Order — in a grid under the record's own fields, with Add line and Remove line beside it. This is the only place a line is edited: it has no screen of its own and no place in the rail, which is what the third kind of class means (chapter 15). A record with no lines shows no grid, so a master's editor is a form and a button row and nothing else.

The column that points at the parent is not shown. You never fill it in: the application stamps it when you save, which is also why the lines are written after the record — a new record has no id until it is stored, and that id is what the lines are attached to.

Line edits are part of the same copy. Adding, changing or removing a line makes the editor unsaved, so navigating away asks the same question; Cancel discards line changes exactly as it discards a typed field; and removing a line only removes it from the store when you save.

Discard your changes? Because the editor fills the content area rather than opening a window in front of it, you can wander off with unsaved edits — so the application asks first. Clicking a rail item, Back, or Sign out while a record has unsaved changes prompts once; answering no leaves the editor exactly as it was. This is the one interaction the in-place editor adds, and it exists on all three front ends.

If you would rather have the old window

Name the layout. layout tabs is what every earlier version produced — a tab per class, with an editable grid — and sidebar, master-detail and dashboard are the other three shapes described in chapter 8. Together with nologin, layout tabs reproduces the pre-login output exactly.

build app: a shop that sells books layout tabs nologin

The web application has no window and therefore no layout: it is always this shell.

17. The chat page

Every command in this manual is typed at the console prompt. chat opens the same tool as a page in your browser instead: you type a command, its whole output appears below what you typed, and a header always says which solution is loaded and which project the next command will act on. Type ui if you prefer the shorter name.

The page runs inside the tool itself, on a loopback address with a one-time token in the URL. Nothing is published and nothing leaves the machine. The console that opened it waits while you work, and the address is printed there in case the browser does not open by itself.

Before you have typed anything the page offers four commands to start with. Clicking one fills the box; none of them runs on its own. The page follows whichever of light or dark your operating system is set to, and changes with it — there is no setting of its own to get out of step with.

Loading a solution

Until now the tool worked wherever it was started, or wherever PROJECTPATH pointed. Change… in the header opens a panel that takes a path to a .sln, a .slnx, a .csproj or a folder, and the list under the box walks the filesystem so you can click your way there instead. Solution files are listed first, because that is usually what you came for. The panel closes itself once a path loads, and it is already open when the tool starts somewhere with no projects in it — there, choosing somewhere else is the first thing to do.

A solution is rooted at the common ancestor of the projects it declares, not at the folder the solution file happens to sit in. Many solutions keep the .sln in a folder of its own with every project a sibling of it; rooting at the file's own folder would find none of them.

Loading moves the whole session, the console included — there is one workspace, and the transcript says so when it changes. Loading a folder registers every .csproj beneath it; loading a solution registers only the projects that solution declares.

The project tree

Tree in the header shows the loaded workspace down the left, laid out the way Solution Explorer lays it out: the solution at the top, the registered projects under it, the folders each project keeps its files in, and then what a class declares. The top row names what was loaded — Solution 'Acme' (4 projects) when a solution was loaded, Folder 'Acme' when a folder was — and collapsing it collapses everything. It says what the session loaded and never goes looking: a repository can hold several solution files, and only one of them is open.

It opens a level at a time: a project is read when you open it, a class when you open that, so a solution of any size costs nothing until you go looking. Folders come before files and both are in name order. The count beside a project appears once it is open, and is the length of the list underneath it.

Folders are the folders on disk, so a class appears where its file is rather than in one long alphabetical list. Two projects that both have a Models folder open and close independently — the tree keeps them apart by their full path, not by name.

Clicking a class runs show class on it and the source appears in the transcript. Nothing in the tree writes anything on a plain click: the other things it can do are Use, on a project row, which runs use project and moves what the next command acts on — the same command you could have typed, and it appears in the transcript as though you had — and a right-click on a class, which offers the validation page described below.

A class here is a .cs file, which is what the word means to the rest of the tool: list classes lists exactly what the tree draws. A file declaring two types shows once, under the name of the file.

Members are the public data and public methods a type declares — a record's parameters included. A spanner marks a property and a box a method. Computed properties and static members are left out, because neither is data the type carries.

Every row carries the glyph of what it is: a stack for the solution, a window for a project, a folder for a folder, a sheet for a class. Each has its own colour as well, but no two rows are told apart by colour alone.

The tree hides itself on a narrow window, where a fixed pane would leave nothing to read the conversation in. Whether it is showing is remembered for as long as the chat session lasts, including across a refresh, and both tabs of one session agree about it.

Adding a validation from the tree

Right-clicking a class in the tree offers one thing — Add validation… — and clicking it opens a page about that class. A menu rather than opening the page straight away, because a right-click that moves the page without asking is one you learn not to use.

The page names the class and the file it lives in, lists the properties you can refer to with their types, lists the rules already on the class, and gives you a box to type in. Phrasings I understand at the foot opens the whole list of accepted sentences, which is asked of the parser itself — it cannot list a phrasing the tool would refuse.

One rule per line, and each line names the property it is about:

Age must be at least 18
Name must be at most 50 characters
Email must be a valid email
Either Email or Phone must be provided

You never say whether a rule is a field rule or a business rule. The parser that recognizes the sentence is the thing that knows, so Age must be at least 18 and Either Email or Phone must be provided go in the same box.

Each check is written into the class's own source file, inside a Validate() method the tool creates the first time and adds to afterwards. Every check is preceded by the rule as you wrote it, as a comment — that comment is what you read to see what the class validates, and it is also how the tool knows a rule is already there. The file is compiled before it is saved, and if the edit would break a file that compiled before, nothing is written.

The page stays where it is after a successful add, with the new rule now in the list, so a second rule does not mean going back and right-clicking again. A line is added to the transcript as well, so the conversation stays the record of what the tool did.

It refuses, and writes nothing at all, when:

WhenWhat it says
It cannot turn the sentence into a ruleThe sentence back, in quotes, beside the properties and the accepted phrasings

Reading a command's output

Each exchange is a card: what you typed across the top with the time it ran, and what came back underneath. The card is tinted by how the command turned out, exactly as the terminal is: green when it worked, red when it was understood and could not be done, amber when the words were not understood. The verdict is written out as well as coloured — Succeeded, Failed, Not understood or Declined — because the last two share one colour and are not the same thing.

Ending the session

Type exit in the page, close the tab, or press Ctrl+C at the console. chat needs a browser. In a piped or scripted run, or with CG_NO_WEB=1 set, it declines and says so; the console prompt is unaffected.

CommandDescriptionExample
add business validation <rule> in <class name>Adds an entity-level business rule, spanning more than one property: comparisons (after, before, must not exceed), required-when, either/or, arithmetic (equals A times B, plus, minus, divided by) and sameness (same as, different from).add business validation EndDate must be after StartDate in Booking
add validation <rule> on <property> in <class name>Adds a field-level data rule to a class in plain English. Understands required (or 'should not be blank'), numeric bounds (between, at least, at most, greater/less than, positive, not negative, not zero, whole number), text bounds (length between, at most <n> characters, starts or ends with, contains, uppercase, digits only), named formats (email, URL, phone number, postcode, GUID, IP address, date), relative dates (in the past, in the future, at least <n> years ago, within the last <n> days), must match <regex>, and a list of allowed values.add validation must be between 18 and 65 on Age in Employee
generate validatorGenerates a validator for a class.generate validator for Employee
show business validation <class name>Show business rules for a class.show business validation Booking
show validation <class name>Show data validation rules for a class.show validation Employee
