SmartCodeGenerator

User Manual

A command-line assistant that turns plain-English descriptions and existing data into working .NET projects.

1. About this manual

SmartCodeGenerator is an interactive command-line tool. You type instructions in ordinary English — create employee class, build app: a library that lends books to members — and it creates or edits real .NET code on disk.

This manual covers the tool as an end user meets it: how to start it, what each command does, and how to drive the two flows that do the most work — generating a whole application, and editing the classes of a project. Chapter 15 is a complete command reference you can skim.

2. Getting started

Starting the tool

Ask it for its version with CodeGenerator --version, or for the command overview with CodeGenerator --help (-h and /? also work), without entering the prompt at all.

Run the executable with no arguments and it prints three lines — the first naming the version you are running — and the prompt:

CodeGenerator >>

Type help for an overview of what the tool can do, and exit to leave. Press TAB at the prompt for command suggestions.

Colour, and turning it off

Output is colour-coded: green when something succeeded, red when it failed, yellow for a warning you should read, and grey for secondary detail such as a path. Colour is switched off automatically when you redirect output to a file or another program, so a saved transcript is ordinary text. To turn it off at a real console as well, set the NO_COLOR environment variable to anything at all — the convention is that its mere presence is the instruction.

A quiet start is a healthy one. The tool reports its own state only when something is wrong with it — a missing Wikipedia store, nothing updating it, an AI model it was told to load and could not. So if all you see is those three lines, everything it depends on is in order. Type status at any time for the full picture. Earlier versions printed that picture at every launch, which meant the warnings in it were easy to skim past.

Where your work is saved

Everything the tool creates goes under a single folder called the workspace root. It is chosen like this, in order:

  1. the PROJECTPATH environment variable, if it is set;
  2. otherwise the current directory — and if you launched from a build-output folder such as bin\Debug\..., the tool climbs out of it so generated code does not end up buried there.

Check yours before you generate anything. On Windows, echo %PROJECTPATH% tells you where your projects will appear. Setting it once saves confusion later, because the tool reports the full path of everything it writes and that path will not be your current directory if the variable is set.

Running a single command without the prompt

Pass a command as an argument and the tool runs just that command and exits, through exactly the same pipeline as the interactive prompt:

CodeGenerator "create console project EmployeeManagement"

Scripting the tool

You can pipe a sequence of commands into the tool. When input is piped, it never prompts — every question that would normally be asked is skipped, so a script always produces the same result. Anything you would have answered interactively must instead be typed on the command line (see chapter 7):

build app: a shop that sells books company "Codis Ltd" theme dark
approve console
exit

3. Core ideas

Projects

A project is an ordinary .NET project on disk, inside your workspace root. One project is current at a time, and class commands act on it. Use list projects, use project <name> and current project to move around.

Two ways to create code

FlowUse it whenChapter
build appYou want a whole working application — model classes, data access, validation and a front end — from a description or a data file.4–8
Project and class commandsYou want to build up or edit a project piece by piece: classes, properties, methods, interfaces, validation rules.9–11

The .codegen folder

The tool keeps small files of remembered state beside your work, including the customization answers it offers back to you next time (.codegen/app-profile.json, chapter 7). They are safe to delete; you will simply be asked again.

4. Building an application: the guided flow

The build app command is the centre of the tool. It asks a short series of questions, works out a candidate set of classes, shows them to you, and only writes code once you approve.

Starting it

CommandEffect
build appAsks for the description first, then everything else.
build app: <description>Skips the description question — you have already answered it.

The questions, in order

  1. What are you building? A sentence of plain English: a library that lends books to members. Press Enter to skip it if you are pointing at a data file instead.
  2. Which kind of application? Chosen from a list — see chapter 8.
  3. Do you have existing data? If yes, you name the format and the file, and the file becomes the source of truth for the model (chapter 5).
  4. Customize appearance and features? Optional. Answering n keeps the defaults; answering y opens nine short prompts — ten for a WPF or Windows Forms application, which is also asked its window layout (chapter 7).

At any question, c cancels the whole thing and nothing is written.

Discovery

From a description, the tool works out which classes your domain needs. It reads a local Wikipedia knowledge store and may fetch from Wikipedia the first time it meets a topic, which is why the first run on a new subject can pause for a moment. It then prints the candidate model — each class, where it came from, its fields, and any relationships it found:

Candidate model (10 classes):
  - Shop [Seed] { Name:string, Address:string, City:string }
  - Book [Wiki] { Title:string, Author:string, Isbn:string, Published:DateTime }
  - Manuscript [Wiki] { Number:string, IssuedOn:DateTime, BookId:int }  -> Book

[Seed] means the class came from your own words; [Wiki] means it was read out of an article. The arrow shows a relationship the tool inferred.

If no topic is recognized the tool says so and shows only the classes it took from your words. A very short description — two or three words — often finds nothing. Add a few more words about what the system does, or add the classes by hand in the review loop.

5. Building from your own data

If you already have the data, it is a better source than any description: the tool reads the real columns and types instead of guessing. There is no Wikipedia lookup on this path, so it is fast and works offline.

Naming the source inline

build app: order tracking from csv D:\data\orders.csv
build app from excel D:\data\shop.xlsx
FormatNotes
csvComma-separated text with a header row.
txtDelimited text.
jsonAn array of objects.
excelAn .xlsx workbook. Each visible sheet becomes a class; hidden sheets are ignored.
sqlRecognized but not supported in this build — the tool tells you so rather than failing quietly.

The location is taken as the rest of the line, because Windows paths contain spaces. Anything you want to add after it must be one of the recognized options in chapter 7 — otherwise it becomes part of the path.

Normalization

Real spreadsheets repeat themselves. The tool inspects what you gave it and reports what it found: a repeating group of columns (Item1, Item2, …), a column that depends on only part of the key, a value that should be its own table. Each finding is offered with an explanation, and you choose which to apply. Applying a finding splits the data into properly separated classes; declining keeps your columns exactly as they are.

Every change you accept is remembered, so why in the review loop can explain a class you never named yourself. When input is piped, add normalize to the command line to accept every finding, or leave it off to accept none — that way a script is deterministic.

Your rows come with it

Rows from your file are written into the generated project as starting data, and loaded on first run. If a row cap applied, the tool says so out loud rather than silently dropping data.

6. Reviewing the model before anything is written

Nothing is generated until you approve. The review loop prints the model, the application type, and any customization you chose, then waits. When a console is available you pick actions from a list; when input is piped you type them.

ActionWhat it does
approve (a)Generates the application. See below for the options.
add <name>Adds a class. The name keeps the shape you type, so add cash register becomes one class.
remove <name>Removes a class.
rename <old> <new>Renames a class.
field <class> <name>[:<type>]Adds a field. Omit the type to have it inferred; explicit types are string, int, decimal, bool, DateTime.
unfield <class> <name>Removes a field.
why [name]Explains the tool's decisions. Bare, it groups every decision by outcome; with a name, it shows that name's whole trail — the stage, the reason, and the evidence.
cancel (c)Abandons the model. Nothing is written.

Approving

approve                  generates using the type you chose at the start
approve webapi           overrides the type
approve webapi sqlite    ...and uses a SQLite database instead of JSON files

Interactively, approve asks for the type and (where it applies) the storage backend through pickers, with your earlier choice pre-selected so Enter simply confirms it.

An empty model cannot be generated — if discovery found nothing, add at least one class first.

7. Customizing the generated application

By default the generated application is plain and unbranded. You can change how it looks, what it is called, and which optional layers it contains.

Three ways to set it

On the command line

Options go last on the line, after any data source:

build app: a shop that sells books company "Codis Ltd" theme dark accent #0B6E4F
build app: a shop that sells books layout sidebar theme dark
build app: order tracking from csv D:\data\orders.csv company "Codis Ltd" noseed

Through the wizard

Answer y to Customize appearance and features? and the tool asks nine short questions — ten for a WPF or Windows Forms application, where the window layout is asked first — each showing the value it would keep in brackets. Press Enter to accept what is shown, or type none to clear an optional one:

  Layout [tabs/sidebar/master-detail/dashboard] [tabs]>
  Company name [Codis Ltd]>
  Theme [light/dark] [dark]>
  Accent colour (#rrggbb) [none]>
  Icon path (.ico or .png) [none]>
  Window title [{company} - {app}]>
  Namespace prefix [CodisLtd]>
  Validation layer [yes]>
  Logging [no]>
  Sample seed data [yes]>

The layout question is asked only for the two windowed application types, because it is the one structural choice in a step that is otherwise decoration — a console or Web API build has no window to shape. It is asked first for the same reason.

Two of them offer you something derived from an earlier answer: naming a company adopts the {company} - {app} title, and a company you have just typed is offered as the namespace prefix with the spaces removed. Both are only suggestions — the bracket shows exactly what Enter will accept.

Answering n at the gate is not the same as cancelling: the build goes ahead with whatever the command line already asked for. Typing c cancels.

From last time

Your answers are remembered in .codegen/app-profile.json and offered back as the starting point on the next run. Options typed on the command line always win over remembered ones. The remembered profile is deliberately ignored when input is piped, so a script cannot be changed by a file it never mentioned.

The settings

OptionEffect on the generated application
company "<name>"Sets <Company>, <Authors> and <Copyright> in the project file, adds a // Copyright (c) <year> <name>. banner to every generated C# file, and — unless you override the title — puts the company in the window title.
title "<pattern>"The window or page title. {company} and {app} are substituted, so "{company} - {app}" gives Codis Ltd - Shop. With no company the placeholder and its separator disappear cleanly rather than leaving a dangling dash.
layout tabs|sidebar|master-detail|dashboardChooses the shape of the window for the WPF and Windows Forms types — see Window layouts in chapter 8. tabs is the default and what every earlier version produced. Named for a type with no window, it is ignored and the tool says so at approve.
theme light|darkColours the desktop front ends. WPF gets a theme resource dictionary merged into the application; Windows Forms gets the colours applied directly.
accent #rrggbbAn accent colour. Valid on its own — "the normal look, in our colour". A malformed colour is ignored rather than failing the build.
icon <path>Copies a .ico or .png into the project as the application icon. A .ico also becomes the icon the built .exe carries.
namespace <prefix>Puts the generated code under your own namespace root: CodisLtd.Shop.Models rather than Shop.Models. The project name, the folder, the assembly name, the database file and the connection-string environment variable are all deliberately left alone — only namespaces move. namespace none clears a remembered prefix. Unlike the other settings, a prefix that is not a legal C# namespace is refused rather than ignored, because it would not compile.
novalidationOmits the validation layer entirely — no Validation folder and no per-class validators.
loggingAdds a small logging layer (off by default). The repository logs each write, and each rejected write when validation is on.
noseedOmits the generated sample rows. Rows imported from your own data file are unaffected — those always come with the project.

One quirk worth knowing. Options are read from the end of the line backwards, so a description whose final words happen to spell an option is read as that option. Put the description first, or quote it, and this never bites.

8. What gets generated

Application types

TypeName to typeWhat you get
WPF (default)wpfA windowed CRUD application. One tab per class by default, or any of the four shapes below.
Windows FormswinformsThe same, built on Windows Forms — the same four shapes.
ConsoleconsoleA menu-driven CRUD application.
Web APIwebapiA minimal API with REST endpoints per class.
Class libraryclasslibThe shared core only — no entry point.
WorkerworkerA background service that exercises the repositories.

Window layouts

The two windowed types can be generated in four shapes. Set it with layout <name> on the line, at the wizard's first customization question, or leave it remembered from last time. Every shape has the same grid, the same Add / Delete / Save row and the same status line — what changes is how you move between classes.

Name to typeWhat the window looks like
tabs (default)One tab per class, its grid filling the tab. What every earlier version produced, and still exactly that.
sidebarA list of classes down the left, the selected one's grid beside it. Suits a domain with more classes than fit comfortably across a tab strip.
master-detailTabs as above, with an edit form under the grid showing the selected row field by field. Easier than editing in grid cells when a class has many fields. Id is shown but not editable, as in the grid.
dashboardOpens on a home screen of cards, one per class, each showing its current row count. Clicking a card opens that class's grid; Home returns to the cards. The counts update as you add and delete.

The layout changes the window only. The classes, the repositories, the validation rules and the storage are identical whichever you pick, so it is safe to regenerate an existing project with a different layout — and a project generated without naming one is byte-for-byte what it always was.

Storage

By default each class is stored in its own JSON file beside the built executable — no database, nothing to install. Add sqlite at approve for a real database through EF Core instead; the schema is created on first run. The connection string can be overridden at run time with an environment variable named after the project, such as SHOP_DB.

SQLite is available for every type except WPF and Windows Forms, whose shared view models read the JSON store directly. The tool tells you rather than generating something that cannot work.

The project layout

Shop/
  Shop.csproj
  Models/        one file per class
  Data/          the store, one repository per class, sample data
  Validation/    the rule interfaces and one validator per class   (omitted by novalidation)
  Logging/       AppLog.cs                                          (only with logging)
  Assets/        your icon                                          (only with icon)
  Views/ ViewModels/   the front end, for the desktop types
Shop.Tests/      a companion test project, generated with the app

Each class gets a typed repository with GetAll, GetById, Create, Update and Delete. Each validator comes in two halves: a .Generated.cs file that is rewritten every time, and a .Custom.cs file that is written once and left alone afterwards — that is where your own rules go, and regenerating will not discard them.

After it generates

Writing the files is not the last step. The tool compiles what it has just written and tells you the result, so you find out that the application builds from the tool rather than from your own first attempt:

Generated project at D:\Work\Shop

Building...
Build succeeded (4.1s)

Run it now? [y/N]: y
Started Shop.exe

Next steps:
  Run it       dotnet run --project D:\Work\Shop
  Seed data    D:\Work\Shop\Data\Seed\   (edit these, then re-run)
  Tests        dotnet test D:\Work\Shop.Tests

Answering y starts the application in a window of its own and hands the prompt straight back, so the tool stays usable while your application is open. Close the application when you are done with it; the tool does not wait for it and will not close it for you.

A class library is never offered, because there is nothing in one to start — it is told how to be referenced instead. If the build fails, the run offer is skipped and the errors are listed with the command to try again:

Build FAILED (2.7s) — 1 error
  Models\Order.cs(14,20): error CS0246: The type 'Custmer' could not be found
  Rerun with: dotnet build D:\Work\Shop

Ten errors are shown at most, and the rest are counted — a project that fails usually fails the same way many times over, and the first few say what went wrong. The next-step lines are printed whether the build passed or failed, because a project that does not yet compile still has seed data you may want to look at.

The build and the run offer happen only when you are typing at the prompt. A piped or scripted run does neither, so existing scripts are unchanged and no script is made slower by a compile it never asked for. The next-step lines are always printed.

Regenerating over an existing project

Running build app again against an existing project reuses it: generated sources are overwritten, but the project file and anything you have edited by hand are left in place.

Because that is not always what you meant — two descriptions can easily arrive at the same name — you are asked first:

D:\Work\Shop already holds a generated project.
Regenerating overwrites its generated sources — Models, Data, Views and the
*.Generated.cs validator halves. Your .Custom.cs rules, the project file and
anything you added yourself are kept.

  [o]verwrite   [r]ename   [c]ancel   (Enter cancels)
AnswerWhat happens
oRegenerates in place, as described above.
rAsks for another name and generates under that instead, leaving the existing project untouched. The name is tidied the same way a name taken from your description is, so cash book becomes CashBook. If the new name is also taken, you are asked again.
c or EnterWrites nothing and returns you to the review loop. Your model is not lost — you can rename, adjust it and approve again.

Pressing Enter cancels rather than overwrites, deliberately: the effortless answer is the one that cannot lose work. The question is asked only when a project of that name is already there, so it never interrupts a first build, and — like the build and the run offer — it is skipped entirely when input is piped, where the old overwrite-without-asking behaviour is kept so that scripts are unchanged.

12. AI-assisted recognition

The tool recognizes commands by rule first. Optionally it can also use a local AI model to work out what an unrecognized line probably meant. It is off by default, runs entirely on your machine, and only ever suggests — it never runs a command you did not confirm.

CommandWhat it does
ai enable / ai disableTurns it on or off. After enabling, restart the tool to load the model, then run ai reindex.
ai status (or just ai)Whether it is on, the model and index in use, both confidence gates, and how many decisions have been logged.
ai reindexRebuilds the phrase index from the current commands. Run it after enabling, or whenever ai status reports REINDEX REQUIRED.
ai whyExplains the last AI reading: what you typed, how it was read, the supporting examples, and whether you accepted it.
ai mode retrievalHow unrecognized input is read. Only retrieval works today; generative and hybrid are declined.

Learned commands

The tool also remembers corrections you make, so a phrasing you use often is recognized next time.

CommandWhat it does
show learningLists learned command signatures and their confidence. Also list learning, view learning.
reset learningClears the learned memory. Also clear learning, forget learning.

13. Two worked examples

A branded desktop application from a description

CodeGenerator >> build app: a library that lends books to members company "Codis Ltd" theme dark
  1. Choose WPF when asked for the application type.
  2. Answer no to existing data.
  3. Answer n to the customization step — the command line already said what you wanted.
  4. Read the candidate model. Remove anything irrelevant (remove Manuscript), add anything missing (add late fee), then approve.
  5. Wait for the build the tool runs for you, then answer y to Run it now?. The window is titled Codis Ltd - LibraryThatLendsBooksToMembers, painted dark, and every file carries the copyright banner.

A Web API from a spreadsheet

CodeGenerator >> build app: order tracking from excel D:\data\shop.xlsx
  1. Choose Web API.
  2. Read the normalization findings and accept the ones that make sense.
  3. approve webapi sqlite to store the data in SQLite instead of JSON files.
  4. Answer y to Run it now?; the REST endpoints serve your own rows. The address it listens on is printed as the application starts.

14. Troubleshooting

What you seeWhat it means
Generated files are not where you expectedPROJECTPATH is set and points elsewhere. The tool prints the full path of everything it writes — trust that over your current directory.
"No topic recognized online"The description was too short or too unusual to match an article. Add a few words about what the system does, or add the classes by hand in the review loop.
"Nothing to generate — the model is empty"Discovery found no classes. Add at least one with add <name> before approving.
Building the generated project reports a file it cannot find, and the file is plainly thereThe path is too long for Windows. Generate under a shorter workspace root.
The window has tabs when you asked for another layout, and the project has a longer name than you expectedThe option was typed before the data source instead of after it, so its words stayed in the description — build app: a shop layout sidebar from csv … builds a tabbed app called ShopLayoutSidebar. Options go last on the line. The review loop lists the settings it actually read, which is where to check.
"The … layout applies to the wpf and winforms targets"You named a layout but approved a type with no window. The application is still generated; only the layout is ignored. Approve wpf or winforms to use it.
SQLite was refused for a desktop applicationWPF and Windows Forms read the JSON store directly. Choose another type, or keep JSON.
Your own validation rules disappearedThey should not: rules go in <Class>Validator.Custom.cs, which is written once and never rewritten. The .Generated.cs half is the one refreshed each run. The single exception is the file's own namespace line, which is repointed if you change the namespace prefix — otherwise the file would no longer compile alongside the rest of the project. Your rules themselves are never touched.
Startup no longer shows the store's dump date, or whether AI is onBy design: the tool is quiet when nothing is wrong with it, so that the warnings it does print are noticed rather than skimmed. Type status for the full picture, which is the same information.
"Something went wrong", and you need more than the messageSet CG_VERBOSE=1 and run it again: the error then includes the internal exception type and where it happened, which is what to quote if you report the problem. That detail is hidden by default because it is not something you can act on.
A piped script behaves differently from typing the same commandsBy design: piped input never prompts, and the remembered customization profile is ignored. State what you need on the command line.
"Build FAILED" straight after generatingThe application was written to disk but does not compile. The errors listed are the compiler's own, against the generated files — the most common cause is a class or field name that is not valid C#. Fix it in the review loop and generate again, or edit the reported file directly and dotnet build. Nothing about the project is lost either way.
Nothing is built after generating, and there is no Run it now?Input is piped. The build and the run offer are for typing at the prompt only, so a script is never slowed by a compile it did not ask for. Build it yourself with the command in the next-step lines, which are printed either way.
"Build timed out"The compile ran past three minutes and was stopped. This says nothing about the generated code — a first build on a cold machine can simply be slow. Run dotnet build on the reported folder yourself.
"Could not start dotnet"The .NET SDK is not on PATH for this session. The application is written and intact; install the SDK, or open a shell that has it, and build the reported folder.
You answered y to Run it now? and no window appearedLook for it behind the terminal — it opens as a separate window and does not steal focus. A Web API and a worker have no window and open a console of their own instead.
"… already holds a generated project" for an application you have never builtTwo different descriptions reduced to the same project name — a shop and the shop system both give Shop. Answer r and give it a name of your own; the existing project is left alone.
You meant to overwrite and it did nothingEnter cancels at that question, on purpose. Answer o to overwrite. Nothing is lost either way — the model is still in the review loop, so simply approve again.
Your edits to a generated file are gone after regeneratingAnswering o overwrites generated sources, which includes any changes you made inside them. Only <Class>Validator.Custom.cs, the project file and files you added yourself are preserved. Put your own code in new files, or in the .Custom.cs halves.

build app: <description> [customization options]Customizes the generated application. Options go LAST on the line, after any data source: company "<name>" sets the company (used in the project metadata, the window title and a copyright header); theme light|dark and accent #rrggbb colour the desktop front ends; icon <path> supplies a .ico or .png; title "<pattern>" overrides the window title, where {company} and {app} are substituted; namespace <prefix> puts the generated code under that namespace root (CodisLtd.Shop), leaving the project and assembly names alone; layout tabs|sidebar|master-detail|dashboard chooses the shape of the window (wpf and winforms only).build app: a shop company "Codis Ltd" namespace CodisLtd theme dark layout sidebar
build app: <description> [novalidation] [logging] [noseed]Chooses which optional layers are generated. 'novalidation' omits the Validation folder and its per-model validators; 'logging' adds a logging layer (off by default); 'noseed' omits the sample seed rows (rows imported from your own data file are unaffected). Interactively these are asked by the 'Customize appearance and features?' step, which remembers your answers in .codegen/app-profile.json.build app: a shop novalidation logging noseed
